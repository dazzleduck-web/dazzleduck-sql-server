Ingestion topology

DazzleDuck Ingestion Path

Many clients per queue, a handful of queues per server, one writer thread each — and a single transaction where the Parquet files and their catalog entry land together.

Why the bucket exists

Clients send small batches constantly. Writing each one straight through would produce a tiny Parquet file per batch. The bucket trades a bounded delay for file size, flushing on whichever of min_bucket_size or max_delay_ms comes first.

One writer, on purpose

Each queue has a single writer thread. Parallelism comes from running several queues, not from several writers on one queue — which keeps each queue's output files and its ordering guarantees straightforward.

The commit is the boundary

A batch's files are registered in one transaction. Either all of them are visible, or none are: the queue deletes local files it knows were not registered, and the rest stay as orphans until ducklake_delete_orphaned_files runs.

What the picture leaves out

Producer de-duplication, back pressure when pending writes exceed the limit, and the compaction job that later merges these files. Each is real; none changes the shape above.
